# 从“让舵机转一下”理解这个框架

这是一份可以跟着代码持续更新的导读。它用一个简单问题贯穿全文：**上层说“转到 60°”，系统为什么不会盲目照做？** 文档中的“已实现”只指仓库当前代码；“下一步”是设计目标，不代表已经接上真实硬件。

## 先看一次完整旅程

当前示例在 [`examples/demo.c`](../examples/demo.c) 里手工准备三样东西：运动限制、目标命令和假传感器。它调用：

```c
er_runtime_submit_command(&rt, &cmd);
er_runtime_arm(&rt);
er_runtime_step(&rt, now_us, &sensor, &out);
```

可以把它想成机场安检：`command` 是旅客想去哪里，`sensor` 是实时仪表告诉我们的当前位置，`step()` 是安检员，`output` 是“这一次允许发给执行器的结果”。在这个单次调用示例里，输出只打印到终端。完整仿真则由 `sim/runner.c` 或浏览器反复推进；**还没有真实 PWM、CAN、RTOS 周期任务或舵机驱动**。`enabled=1` 只表示核心允许输出，不表示舵机已经动作。

## `step()` 每次做什么

源码在 [`src/runtime.c`](../src/runtime.c)。每个周期依次检查：

1. 时间是否倒退，周期是否超过上限。
2. 传感器是否有效、是否过期、是否为 NaN、是否越过位置范围。
3. 命令是否存在、是否过期。序列号和目标范围检查在 `submit_command()` 中完成。
4. 所有检查通过后，按位置误差计算一个速度，并限制在命令允许值内。

任一安全检查失败就锁存 fault、撤销 `armed`、清零输出。这样一次失效不会因为下一次数据碰巧恢复就自动重新运动。当前算法是固定双关节的教学级比例位置到速度计算，**不是 FOC，也不是完整的真实舵机安全闭环**。实际产品仍需把“输出禁用”连接到驱动器的制动、STO 或断能动作，并用示波器验证延迟。

## 为什么命令、传感器、输出要分开

“目标是 60°”和“现在到了 60°”是两件事。普通 PWM 舵机可能只有命令接口，没有真实位置反馈；总线舵机可能提供位置、温度和故障反馈。统一接口必须声明能力，不能把“命令已发送”冒充“动作已完成”。接口草案在 [`include/er/hal.h`](../include/er/hal.h)，包括反馈、使能、位置、速度、扭矩和 PWM 能力。

## 硬件怎么被替换

```text
应用/能力组件
      ↓ 统一设备接口
舵机或电机驱动
      ↓ CAN / UART / PWM / ADC
板级驱动和芯片 SDK
```

Linux 仿真时，最底层可以是一个内存里的“虚拟舵机”；上板后替换为 PWM 舵机或总线舵机。上层仍然只看到目标、反馈、状态和错误码。`hal.h` 是边界定义，具体驱动尚未完成。

## OTA 现在是什么

[`src/ota.c`](../src/ota.c) 目前是内存中的流程原型：下载到某个槽、完成校验、选择试启动、确认新版本或标记失败。`verify` 只是调用外部回调，并不自己计算哈希或验证签名；它还没有真实 Flash、掉电持久化和 Bootloader 配合，因此不能用于量产升级。完整目标见 [`docs/ota.md`](ota.md) 和 [`docs/requirements.md`](requirements.md)。

## 怎么阅读和运行

```sh
cmake -S . -B /tmp/er-build
cmake --build /tmp/er-build
(cd /tmp/er-build && ctest --output-on-failure)
/tmp/er-build/er_demo
```

先读 `demo.c`，再读 `runtime.h` 看数据结构，最后读 `runtime.c` 看检查顺序。修改功能时同步增加测试；测试使用显式检查，不依赖会被 Release 构建删除的 `assert()`。

## 持续维护规则

每次新增能力都更新三处：

- 在本文补一个“输入 → 检查 → 输出”的故事和源码链接。
- 在 `docs/requirements.md` 写清验收条件。
- 在 `tests/` 增加能失败的自动化用例，并记录仿真验证还是硬件验证。

最后更新时间：2026-11-12。本文随代码提交一起维护。

## 2026-11-12：闭环仿真已经接入

`demo.c` 仍是单次计算示例；新增的 `sim/runner.c` 则运行 300 个虚拟周期并输出 JSONL。网页通过 `web/wasm/bridge.c` 调用同一份 C 核心，展示舵机追踪目标的过程。命令超时和传感器失效可以复现，卡死模型尚无堵转保护。详情见 [场景测试](scenarios.md) 和 [浏览器接口](../web/protocol.md)。

## 现在打开网页，你在看什么

从 [README](../README.md) 启动网页后，先确认后端标识为 **C11 核心 · WebAssembly**。从“目标 60°”到摇臂运动的过程是：

```text
滑块 / 自动化命令
        ↓ app.js 校验入口数据
WASM 桥接 → C 控制核心检查并计算速度
        ↓
虚拟舵机按速度更新位置 → 反馈给下一周期
        ↓
同一份位置数据 → 3D 摇臂 + 曲线 + JSON 观测
```

模型没有直接转向目标的独立动画。蓝色目标件是“希望到哪里”，实际摇臂是“仿真算到了哪里”。界面里的型号标签只是外观说明，不代表核心已经实现飞特串口协议。

HD1910M 黑色壳体、舵盘和贴面文字由 `web/servo3d.js` 的程序化几何绘制。仓库已保存官方 STEP 和转换 STL，但当前主视图不是完整 CAD 渲染，更没有负载、碰撞或齿隙计算。它服务于理解控制状态，不用于加工或机械装配验收。

## 怎么证明不是只做了一段动画

有 Node 的构建注册 10 项测试：两个原型测试、设备绑定与仿真驱动测试、四个桌面场景、C 桥接测试和实际 WASM 网页适配测试。桌面每个场景运行 300 步，网页事件可导出/导入回放。命令超时和传感器故障会检查禁能结果；卡死场景目前只验证轴停止，不能宣称有堵转保护。

测试只对覆盖到的条件负责。例如 OTA 正常路径测试通过，不代表已经做了签名校验或掉电回滚。测试机制可用和功能完整是两件事。

## 下一阶段还缺哪些连接

执行器 HAL 已接入仿真绑定，但尚未接到真实驱动；`ports/` 是适配说明，尚未运行 FreeRTOS/RT-Thread。参数存储、设备日志、产测和完整 OTA 也仍在需求/设计阶段。AI 可以使用命令/观测接口，但目前没有接入模型或自主训练任务。

后续先按 [需求基线](requirements.md) 的阶段完成这些连接；每项同时更新验收条件、测试和本文，不能以外观优化代替平台功能进度。

## 从直接连接到可替换设备

现在运行链路变成：

```text
启动代码创建静态仿真设备 → er_devices_bind 检查能力
每周期：接口读取反馈 → runtime 计算 → 接口写入速度/使能
仿真环境推进模型 → 下一周期
```

有反馈设备满足当前闭环要求；无反馈驱动能接收位置命令，但不能冒充闭环反馈设备，绑定时会明确拒绝。仿真中“我们知道模型的位置”不等于实际设备具备位置上报能力。

这验证了设备接口的第一步落地，不代表 RTOS API 已能在 Linux 原样运行。下一层是 OSAL 适配，芯片驱动与中断仍留在目标平台。

## 周期任务如何跨系统复用

新增 `er_periodic_init/wait` 只依赖 `now/wait_until` 接口。Linux 端口调用 POSIX 单调时钟，单元测试替换为虚拟时钟；调度算法不引用操作系统头文件。`er_periodic_demo` 演示实际等待并报告迟到，不是实时电机任务。详细契约见 [OSAL](osal.md)。
